# API·소스 코드 진단: community 1~2단계 반영

## 현재 상태

2026-10-20에 `artex-ko-plus`의 `d30c076`을 참고하여 진단·후보 검토 코드를 선별 이전했다.
기존 community 인증, DB 연결 풀, 다국어 설정, 대시보드, 작업 실행 코드는 유지한다.
첫 반영에서는 DB와 실행 검증을 보류했으나, 이후 사용자의 로컬 적용·검증 승인에 따라
`offensive_candidate_reviews`를 포함한 추가 스키마를 반영했다.
2026-10-20 로컬 개발 DB에서 저장소가 준비되었고, 격리 DB에서
후보 검토 저장·취소·이어하기·복구 테스트를 수행했다. 외부 모델 호출은 수행하지 않았다.
상세 내용은 [후속 반영 완료 기록](complete/2026-10-20-security-followup.md)을 참고한다.

다른 설치에서 아직 스키마를 적용하지 않았다면 기존 준비 상태 검사를 유지한다.
저장소가 없으면 화면에서 AI 검토 버튼을 비활성화하고, 직접 API 요청도 모델 호출 전에 503으로 거절한다.
임시 파일로 대체 저장하는 우회는 추가하지 않았다.

## 사용 흐름

기능 메뉴의 **API·소스 코드 진단**에서 `/offensive/assessments`로 이동한다.
기존 `/dashboard`와 작업·취약점 메뉴는 유지한다.

1. API 진단은 OpenAPI(JSON/YAML, 8 MiB), URL 탐색, HAR(16 MiB) 중 선택한다.
   진단 서비스에서 접근 가능한 API 주소를 입력한다. HAR 원본 주소는 선택 사항이다.
2. 소스 진단은 ZIP(20 MiB)을 등록한다. 대상 코드를 빌드·실행하지 않는 정적 분석이다.
3. 등록된 대상을 선택한다. API는 GET/HEAD 작업을 최대 40개 선택한다.
   필요 시 이번 진단의 인증용 Bearer 토큰을 입력하며, 요청 후 입력값을 지운다.
4. 실행 이력에서 상태, 후보, 근거, 범위 한계, 산출물을 확인·다운로드한다.
5. 준비된 후보 검토 저장소와 기존 LLM 프로필을 사용해 묶음 크기(1~5)를 선택하여 검토한다.
   후보별 판정을 저장하고, 중단 후 미검토 후보부터 이어가며 오류 후보는 뒤에 재시도한다.
   완료 판정은 재처리하지 않는다. 후보 검토는 새 대상 요청·도구 실행·취약점 자동 등록을 하지 않는다.

후보·오류 응답·정적 규칙 일치는 취약점 악용 성공을 뜻하지 않는다.
도구 진단 결과와 AI 판정은 별도 상태로 표시한다.

## 진단 서비스 연결

`Dockerfile.offensive-runner`와 `docker-compose.offensive.yml`은 선택형 진단 서비스 구성이다.
기본 `docker-compose.yml`은 수정하지 않았다. 구성 파일을 추가했다고 서비스가 자동 실행되지는 않는다.

- 앱 설정: `ARTEX_OFFENSIVE_URL`, `ARTEX_OFFENSIVE_TOKEN_FILE`.
- 앱·진단 서비스의 인증 파일: `.secrets/offensive-token`. 두 서비스가 같은 파일을 읽기 전용으로 사용한다.
  인증값은 별도 운영 과정에서 준비하며 문서·로그에 기록하지 않는다. 파일 누락 시 디렉터리를 자동 생성하지 않는다.
- 진단 데이터: 호스트 `data/offensive`를 진단 서비스의 `/data/offensive`에 연결한다.
  기존 앱의 `/app/data`와 같은 호스트 데이터를 사용하므로 업로드 소스의 해시 확인 경로가 일치한다.
- 진단 서비스 포트는 호스트에 공개하지 않고 Compose 내부에서 앱이 접근한다.
- overlay는 `artex-community:local` 앱 이미지를 사용한다. 기본 Dockerfile은 미리 빌드된
  `dist/<architecture>/artex`를 필요로 하므로 이번 변경이 포함된 바이너리와 내장 프런트엔드를 별도로 준비해야 한다.
  기존 global 릴리스 이미지만 실행해서는 신규 API·화면이 생기지 않는다.
- 진단 이미지에 Semgrep·Schemathesis·PyYAML을 구성한다. 기존 Go·프런트엔드 의존성 파일은 변경하지 않았다.
- crAPI·Benchmark·Splunk·AWS 실습 환경은 이번 범위에 포함하지 않는다.
  도구 카탈로그의 설치되지 않은 예제는 준비되지 않은 대상으로 표시된다.
- 로컬 브라우저 확인은 향후 실행 중인 앱의 `localhost` 주소를 사용한다.

## 호환성과 제한

- 기존 `ApiError`·인증 실패 처리·JSON 요청을 유지하고 공통 HTTP 함수에 FormData와 Blob 응답을 추가했다.
- 화면 고정 문구·상태·메뉴는 ko/en/zh/es/ja 메시지에 추가했다.
  모델 판정 언어는 기존 서버 출력 언어 설정을 따른다.
- 가져온 진단 서비스 설명·일부 서버 오류·저장된 자동 판정과 근거 설명은 원문을 유지한다.
  해당 동적 메시지까지 모든 언어로 번역된 상태는 아니다.
- `.dockerignore`에 인증 파일·로컬 런타임 경로를 제외했다.
  모델 입력 및 진단 결과의 `_KEY` 형태 값 가림을 보강했지만,
  업로드 원본에 존재하는 모든 비밀값의 탐지를 보장하는 기능은 아니다.
- 진단용 스킬 파일은 추가했지만 DB 기본 노출 설정은 변경하지 않았다.
  후보별 검토는 이 스킬 노출에 의존하지 않는다.
- 기존 데이터·인증 정보·실행 이력은 복사하지 않았다.

## 이후 필요한 확인

2026-10-20 후속 작업에서 [로컬 Docker 개발 환경](local-development.md)을 기동하고
화면·API·DB·진단 서비스의 기본 연결을 확인했다.
상세 결과는 [개발 환경 완료 기록](complete/2026-10-20-local-docker-development.md)에 있다.
후속 승인 작업에서 후보 검토 저장 테이블을 로컬 개발 DB에 적용하고
후보 저장·취소·이어하기·복구 경로를 격리된 테스트 DB에서 검증했다.
외부 모델을 사용한 실제 대상 진단은 별도로 확인해야 한다.

사용자가 요청할 때만 빌드·테스트·런타임 확인을 수행한다.

- 프런트엔드 타입·다국어 키·정적 빌드, Go 컴파일과 관련 기존 테스트.
- 기존 로그인·대시보드·JSON API·파일 업로드·다운로드 회귀 확인.
- 진단 서비스 미설정·실패, 잘못된 입력·초과 크기·선택하지 않은 API 요청 거절.
- 실제 OpenAPI·URL·HAR·ZIP 등록부터 후보·산출물 조회까지.
- 저장소 없는 환경에서 AI 호출 없이 비활성화되는지 확인.
- 저장소 준비가 별도 허용된 뒤 후보별 저장, 중단·이어하기, 재시작 복구, 중복 실행 방지와 사용량 확인.

기능 구현과 검증 완료를 구분하며, 현재 런타임 정상 동작을 보증하지 않는다.
